# Domain 5 — Context Management & Reliability (15%) — Master Note

Merged compression layer for exam day. Scenarios that carry most Domain 5 weight: Customer Support Resolution Agent (multi-issue context, escalation, identity), Multi-Agent Research System (error propagation, provenance), Structured Data Extraction (calibration), Codebase Exploration (long sessions, scratchpads).

## Task 5.1 — Conversation Context Management

- **Principle**: Summarization is lossy compression that destroys high-value tokens first — amounts, dates, percentages, order/case IDs, customer-stated expectations, exact error strings. Replace older turns with structured summaries, keep recent turns verbatim, and hold transactional facts in a case-facts block injected verbatim into every prompt, outside the summarized history. Trim verbose tool results to the fields downstream reasoning needs before they are appended. Send the complete messages array every request — the API is stateless. Place key findings at the beginning of aggregated input with explicit section headers, because attention is biased toward the start and end (lost-in-the-middle). A sliding window deletes a turn outright while progressive summarization rewrites it lossily - a deleted turn cannot be recovered and a summarised amount is distorted rather than preserved. Lay the prompt out in three zones: the case-facts block at the top (highest attention), trimmed tool results in the low-attention middle valley, and the critical recap plus policy line plus the final question at the end.
- **Why the exam wants this**: The intuitive answer — compact everything uniformly, raise the summarization threshold, or tell the model to remember — is wrong at the layer it addresses. The failure is history management, not prompt content. The exam also separates a sliding window (drops a thread the customer returns to) from progressive summarization of resolved threads while the active thread stays full.
- **Distractors**: "Apply progressive summarization uniformly across the whole conversation" (destroys the transactional spine). "Raise the summarization threshold from 70% to 85%" (delays the loss, does not prevent it — sounds-efficient). "Revise the summarization prompt to preserve all numbers verbatim" (best-effort, not deterministic — sounds-thorough). "Store full history externally and retrieve when the agent detects phrases like 'as I mentioned'" (silent references never trigger the retrieval — sounds-enterprise). "Keep a sliding window of the last N turns" (loses the resolved thread the customer returns to). "Pass full tool responses to maintain fidelity" (noise accumulates across turns). "Put the summary at the end / rotate position between runs" (lost-in-the-middle; rotation only balances on average). "Add 'remember the refund amount' to the system prompt" (the real cause is the missing message history). "Move the case-facts block into the middle for chronological order" (that is the low-attention valley - sounds-tidy). "Instruct the model to pay close attention to the key facts" (a best-effort prompt instruction that does not change where attention falls). "Increase the context window so everything fits comfortably" (capacity, not placement, is not the bug).
- **Exact terms**: case-facts block injected verbatim outside summarized history; `/compact`; full `messages` array on every request; prompt caching on the stable prefix (system prompt + tools + early conversation); trimming at the integration layer before append (a PostToolUse hook is the corpus's trim point); subagents return structured key facts, citations, relevance scores, confidence — not verbose prose or reasoning chains. From the dnacenta module only (not stated elsewhere in the corpus): compaction beta `compact-2026-01-12`, context editing `clear_tool_uses_20250919` / `clear_thinking_20251015`, memory tool `memory_20250818`, `messages.count_tokens` for re-baselining token budgets. Tool-result budget: five tool calls (get_customer ~400 tokens, look_up_order ~350, check_policy ~600, shipping history) run roughly 2,000-3,000 tokens per agentic loop, which is 40,000-50,000 across 10-20 iterations - trim at the hook before append, because cleaning up after the context is already bloated is a failed strategy. A post-tool hook filters and normalises output before the model sees it; a pre-tool hook sanitises before the call. Prompt layout: case-facts top, trimmed tool results in the middle valley, critical recap + policy line + final question at the end.
- **Scenario tie-in**: Support agent where the customer references "the 15% discount I mentioned" 20+ turns ago and the agent answers with a wrong value; multi-agent research where a 75K-token aggregate is cited from the first 15K and last 10K but the middle 50K is missed; a prompt that still misreads the refund amount because the case-facts block sits behind 40K tokens of raw tool output.

## Task 5.2 — Escalation Patterns and Ambiguity Resolution

- **Principle**: Exactly three triggers justify escalation — the customer explicitly requests a human (escalate immediately, do not attempt resolution first), a policy gap or exception the agent cannot decide, and inability to make meaningful progress after legitimate avenues were tried. Sentiment, self-rated confidence, conversation length, and multi-intent messages are not triggers. Neither is task complexity alone - a complicated request that still matches policy is resolvable by the agent, just as a long exam question is still answerable. The golden rule: an explicit human request escalates immediately, with no 'let me try first', no 'why do you want a human?' and no confirming question. Escalation is not a fallback for hard problems - if the policy covers the request, resolve confidently. When the customer is frustrated and the agent has no context yet: acknowledge the frustration and ask one targeted question, do not hand off cold. When a fix is already ready: offer resolve-or-escalate and preserve the customer's choice. On a multi-match identity lookup, ask for an additional identifier (email, phone, order ID) — never heuristically pick, never use a confidence threshold.
- **Why the exam wants this**: This is the densest trap cluster in the domain. Every wrong option is dressed as diligence or empathy: sentiment routing (sounds-helpful), a confidence threshold (sounds-smart), a trained routing classifier (sounds-enterprise), resolve-first-then-escalate (sounds-pragmatic). The tested distinction is explicit signal versus inferred signal.
- **Distractors**: "Escalate because the customer sounds frustrated" (sentiment is not complexity). "Auto-escalate when the model's self-rated confidence drops below X" (uncalibrated). "Deploy a classifier trained on historical tickets to predict escalation" (disproportionate infrastructure for a decision-boundary problem). "Resolve the issue first, then escalate if the customer is still unhappy" (overrides an explicit human request). "Ask the customer to confirm they really want a human" (patronising; explicit means explicit). "Escalate a multi-issue message so a human coordinates both" (decompose instead). "Escalate because the tracking data contradicts the customer" (clear system data is not a policy gap). "Pick the most recently active / most recent order / geographically nearest match" (heuristic on ambiguity). "Have the tool return one ranked best match" (hides the ambiguity). "Confidence scoring above 85% acts autonomously" (wrong-account refunds survive in the confident band). "Escalate because the request looks complex" (task complexity alone is not a trigger; only a genuinely stuck agent is). "Ask why the customer prefers a human before transferring" (the explicit request already answered; explicit means explicit). "Offer the self-service portal instead of escalating" (ignores the explicit request). "Attempt one more resolution step, then escalate" (overrides an explicit human request - the Sarah scenario).
- **Exact terms**: `escalate_to_human` tool with explicit usage boundaries; explicit escalation criteria plus few-shot examples in the system prompt; programmatic precondition / hook for financial thresholds (enforcement is code, not prose); structured handoff fields — `customer_id`, `issue_summary`, `order_id`, `root_cause`, `actions_taken`, `recommended_action`, `escalation_reason`; the human sees the handoff, not the transcript, so it must be complete and self-contained.
- **Scenario tie-in**: Support agent at 55% first-contact resolution that escalates simple photo-proof replacements and autonomously attempts policy exceptions; competitor price-matching request where policy covers price drops on your own site only; `get_customer` returning multiple "John Smith" matches; Sarah's 12-month-old order with confirmed damage and late delivery, writing "I've been dealing with this long enough. I just want to speak to an actual person."

## Task 5.3 — Error Propagation

- **Principle**: How a failure is reported matters as much as the failure. Propagate a structured error carrying failure type (transient / validation / business / permission), what was attempted (specific query, parameters), partial results, potential alternatives (narrower query, fallback source, retry-after), and coverage impact. Distinguish an access failure (could not reach the source — a retry decision) from a valid empty result (the query ran, nothing matched — the empty result is the answer). Subagents do local recovery for transient failures (one to two retries with backoff) and propagate only what they cannot resolve. When one subagent fails, preserve the other subagents' partial results and annotate the gap in synthesis. Subagents must never hold termination authority - aborting the whole pipeline on one failure throws away every other subagent's work, so termination is the coordinator's decision, enforced with a hook. The sneakiest failure is dead silence: an overnight job that ends with no error, no output and no report, so you cannot tell whether it finished or died. Error travels up one layer at a time - a tool signals its subagent (isError / errorCategory), the subagent retries locally, and only what it cannot resolve reaches the coordinator as a structured error.
- **Why the exam wants this**: Silent suppression and workflow termination are both wrong, and they look like opposite virtues — graceful continuation and decisive failure handling. Both destroy recoverability. The clean binary the exam loves is "retry only the access failure".
- **Distractors**: "Return empty results with `status: ok` so the orchestrator continues gracefully" (silent suppression — worst option in any 5.3 question, zero recovery path). "Abort the entire workflow on one subagent timeout" (throws away partial results from the subagents that succeeded). "Return a generic 'search unavailable' status" (strips the type, query and partial results the coordinator needs). "Retry the tool indefinitely until it succeeds" (wastes budget on permanent failures). "Always retry empty results in case data appears" (conflates valid empty with access failure). "Collapse outcomes into a single coverage percentage" (discards which part is retryable — sounds-enterprise). "Catch the exception and log it for later review" (the running model gets no signal — sounds-pragmatic). "Implement retries inside the subagent and return only a generic status" (internal retries are right; the generic status is the defect). When a subagent returns a bare "search unavailable", the correct move is to redesign it to emit structured error context - not to retry blindly, terminate the pipeline, or return empty-as-success.
- **Exact terms**: structured error JSON — `failure_type`, `attempted_query`, `partial_results`, `alternative_approaches`, `coverage_impact`, `is_retryable`, `retry_after_ms`; `isError` flag on MCP tool results; `errorCategory` / `isRetryable`; coverage annotation in the synthesis ("PARTIAL COVERAGE — search agent timeout"); local recovery with exponential backoff, 1–2 attempts, then propagate.
- **Scenario tie-in**: Research pipeline where three of five source categories succeed and two time out; patent database returns "Connection timeout" while industry reports return "0 results found"; corrupted PDF terminates the document-analysis subagent and forces the coordinator to make every routine retry decision.

## Task 5.4 — Large Codebase Context Management

- **Principle**: Extended agentic sessions degrade predictably — the model starts referencing "typical patterns" instead of the specific files and functions it found, gives inconsistent answers about the same code, and makes assumptions instead of checking. The root cause is high-signal early findings diluted by high-volume later exploration. Externalize findings to a scratchpad file that survives compaction and crashes; delegate verbose exploration to a subagent so the coordinator receives only the distilled result; inject a phase summary before spawning the next phase's subagents; checkpoint structured state to a manifest so a crash resumes from the last checkpoint rather than from zero; use `/compact` proactively, before natural degradation. Claude Code will not create the scratchpad automatically - you must instruct it, in the session prompt, in CLAUDE.md (loaded every session, so it also reaches headless CI/CD runs), or hardcoded into the subagent loop. The scratchpad records findings and is not a checkpoint; the manifest is the checkpoint. `/compact` is a typed command that cannot be invoked in a CI/CD pipeline.
- **Why the exam wants this**: Every wrong option treats the symptom as a capacity or sampling problem — more tokens, a larger model, a different temperature, a fresh start. Attention dilution is structural and does not shrink with a bigger window. The manifest pattern is the tested answer for crash recovery: the manifest is the source of truth, not the conversation history.
- **Distractors**: "Use a larger context window so degradation does not occur" (attention dilution is not a token-count problem). "Switch to a larger model with a bigger window" (same error). "Increase temperature to encourage more specific responses" (temperature affects sampling, not retention). "Re-run the whole exploration from scratch with a fresh context" (hits the same wall at the same turn count). "Do everything in the main conversation and `/compact` periodically as it fills" (compaction runs after pollution and is lossy; isolation is cheaper than recovery). "Trust the model to remember earlier findings if asked directly" (that is the failure mode). "Periodically clear context entirely during exploration" (loses valid findings). "Rely on /compact to run automatically in a headless CI/CD job" (/compact is a typed command and cannot be invoked there). "Assume the scratchpad is created automatically" (it is not - the instruction must be present).
- **Exact terms**: scratchpad file (`investigation-scratchpad.md` with file:line findings); Explore subagent for verbose discovery phases; subagent returns a concise summary; `context: fork` in skill frontmatter for isolated skill execution; `allowedTools` to narrow a subagent's toolset; manifest file (`agent-state/manifest.json`) loaded by the coordinator on resume; `/compact`; phase summaries injected before next-phase subagents. The manifest lives at a predictable path inside `.claude` (skills, commands, manifest and scratchpad all under it). Three layers together make silent failures impossible: error layer (structured propagation), context layer (scratchpad + /compact), recovery layer (manifest checkpoint).
- **Scenario tie-in**: A 30+ minute codebase investigation where the model starts naming generic patterns instead of the classes it discovered; a three-phase error-handling refactor across 120 files where phase 1 discovery floods the window; a long multi-agent job that must survive a mid-task process crash.

## Task 5.5 — Human Review Workflows and Confidence Calibration

- **Principle**: Aggregate accuracy masks stratum-level failure — 97% overall can hide 45% on handwritten documents or 42% on one field. Validate accuracy by document type and by field segment before removing humans. Emit per-field confidence (not per-document) and calibrate the routing thresholds against a labeled validation set, so a 0.9 means correct roughly 90% of the time for that field and document type. Route low-confidence or ambiguous-source extractions to human review and spend scarce reviewer capacity on the highest-uncertainty items. After deployment, keep running a stratified audit that samples high-confidence extractions too — novel error patterns appear over time and, by definition, never trigger a low-confidence threshold. Failures cluster in the low-volume, high-stakes stratum while high-volume cases carry the average, and errors on an outlier type are systematic - they compound on the same category rather than appearing as noise. The stratified workflow is: categorise into strata, sample a representative batch per stratum (even a 5% bucket gets its own), measure accuracy per category, then act immediately by routing the failing category to review.
- **Why the exam wants this**: The wrong answers are exactly the ones a busy team would ship — trust the headline number, set a threshold, review only the doubtful cases. The tested boundary is calibrated, field-level, ground-truth-grounded confidence (reliable) versus raw model self-report (unreliable). Carry this into 5.2: it is the same distinction behind "never route identity on a confidence score".
- **Distractors**: "97% meets industry standard, automate" (aggregate metric, no stratum check). "Set the confidence threshold to 0.9 to ensure quality" (uncalibrated number, meaningless without ground truth). "Use document-level confidence to route review" (field variance within a document is the whole point). "Sample only low-confidence extractions for review" (misses novel error patterns in the high-confidence band). "Run more documents through to raise the sample size" (volume does not reveal stratum failure). "Compare against competitor systems" (irrelevant to fitness). "Human review is always required regardless of metrics" (too absolute; calibrated automation is valid). "Upgrade the model for complex cases" (capability is not the missing verification step). "Raise the global 0.80 threshold" (the failures pass above it; confidence must be per field and calibrated). "Add more few-shot examples for the failing category" (a measurement and stratification problem, not a prompt problem). "Errors are statistically expected at 96%" (exactly the aggregate-masks-stratum failure).
- **Exact terms**: per-field confidence objects (`{"value": ..., "confidence": ...}`); calibration against a labeled validation set; stratified random sampling by document type, field segment and confidence band; accuracy reporting per document type and per field within type; reviewer capacity prioritised by uncertainty. Each extracted field carries value, confidence and source region as required schema fields (invoice_number 0.97 top-right header; amount 0.91 bottom table row 12; vendor_address 0.63 unreadable -> human review).
- **Scenario tie-in**: An extraction pipeline at 97% headline accuracy with 45% on handwritten notes; a post-deployment audit that must catch a new document template that fails confidently; routing extractions to a small human review team; a 96%-overall system whose document-level confidence above 80% masks persistent errors in the legal-contract stratum.

## Task 5.6 — Information Provenance

- **Principle**: Attribution has to travel with the claim as structured data, or it dies at the first summarization: the report says "studies show X" with no path back to which study, by whom, when. Require every subagent finding to carry claim plus source URL, document name, supporting excerpt and publication date, and preserve those mappings through every downstream agent instead of flattening them into prose. When two credible sources disagree, annotate both values with full attribution and pass the reconciliation to the coordinator — never average, never silently pick, never omit the statistic. Include publication and collection dates so an apparent contradiction is recognised as a trend (28% in 2022 versus 32% in 2024 is not a conflict). Separate well-established findings from contested ones, and render by content type: tables for financial data, prose for narrative, structured lists for technical findings. Provenance is everyone's responsibility across the pipeline: the search agent passes URL, publication date and domain credibility with every claim (often the first place attribution drops); the analysis agent preserves page numbers, section headings and document metadata; the synthesis agent is the highest-risk point for provenance loss, because that is where multiple sources can be collapsed into one unified claim, so it needs source tags in its instance prompt and output schema; the report agent keeps every citation traceable to the source. Requiring publication and collection dates is a structural schema change, not prompt engineering or retry logic.
- **Why the exam wants this**: The traps are confident and tidy — average the two figures, take the conservative one, drop the disputed statistic, use a uniform bullet format for consistency. Each destroys information the consumer needs. The subagent must not resolve the conflict itself: reconciliation is a coordinator decision made with broader context.
- **Distractors**: "Select the more conservative value when sources conflict" (arbitrary; erases the disagreement). "Average the conflicting values" (fabricates a number neither source reported). "Pick the more recent value without flagging the discrepancy" (erases that disagreement existed). "Omit the statistic when sources disagree" (destroys information). "Silently pick one with a footnote mentioning the discrepancy" (subagent resolving a coordinator-level decision with heuristics). "Include both numbers without marking them as conflicting" (the conflict gets merged away downstream). "Render everything in one uniform format for consistency" (content-format mismatch). "Cite sources in an appendix rather than inline with claims" (attribution dies during synthesis). "Let the synthesis agent merge several sources into one unified claim" (the synthesis step is where provenance dies). "Preserve attribution only in the search agent" (each downstream agent must carry it). "Fix stale data with prompt engineering or retry logic" (require publication and collection dates in the schema instead).
- **Exact terms**: claim-source mapping fields — `claim`, `source_url`, `document_name`, excerpt/relevant passage, `publication_date`, `source_type` (primary etc.); conflicting-values structure with both values, source, note and reconciliation; temporal metadata — `data_as_of`, `source_published`, `retrieved_on`; certainty labelling ("well-established" / "contested" / "single-source"); content-appropriate rendering (table / prose / structured list). Per-agent provenance fields: search agent - URL, publication date, domain credibility; analysis agent - page numbers, section headings, document metadata; synthesis agent - source tags in its instance prompt and output schema; report agent - traceable citations.
- **Scenario tie-in**: Two research subagents returning 40% and 12% growth from credible sources; a synthesis report that must distinguish a contested market-share range (12–18%) from a single-source claim; the same statistic reported for different years; a four-agent pipeline where provenance drops at the search agent or collapses at the synthesis step.

## Escalation decision tree

Read the stem, then apply in order. First matching branch wins.

1. If the customer explicitly asks for a human → escalate immediately, no further investigation, no "let me try first", no confirming question. Structured handoff.
2. If the request falls outside documented policy, or needs an exception or authority the agent does not have → escalate. The agent never invents policy.
3. If a hard rule applies (refund above threshold, regulated workflow, high-impact side effect) → enforce programmatically in the tool or a hook, not by prompt; return a structured "requires approval" result rather than a silent pass.
4. If a fix is already ready and the customer earlier asked for a person → offer resolve-or-escalate in one turn; do not silently act on the account, do not run a long intake questionnaire.
5. If the customer is angry and the agent has no context yet → acknowledge the frustration and ask one targeted question. Not escalation.
6. If the customer is frustrated and the issue is straightforward, with no human request → acknowledge, offer the concrete resolution; escalate only if the customer reiterates the request.
7. If the lookup returns multiple matches → ask for an additional identifier (email, phone, order ID). Never rank, never pick by recency, never threshold on confidence.
8. If several turns have been tried and the agent cannot make meaningful progress → escalate with what was attempted, what failed, and partial results. Do not count failures as the trigger.
9. If a subagent's tool fails → local recovery first (1–2 retries with backoff) for transient errors; propagate only what cannot be resolved, with type, attempted query, partial results and alternatives.
10. If a source is unreachable → that is an access failure: consider retry or an alternative path, and annotate the coverage gap. If the query ran and found nothing → that is the answer; do not retry and do not report it as an error.
11. Never trigger escalation on sentiment, self-rated confidence, conversation length, multi-intent volume, or an automated pre-classifier.

## Recall card

- Summarization destroys numbers, dates, IDs, percentages and customer expectations first — extract them into a case-facts block outside the summarized history and inject it verbatim every prompt.
- Summarize resolved threads; keep the active thread verbatim. A sliding window drops the thread the customer returns to.
- Lost in the middle is structural: findings at the top, details in the middle, action items at the end, with explicit section headers.
- Trim tool results to the fields you need before appending; noise accumulates across turns.
- The API is stateless — send the full messages array, or the agent "forgets" mid-conversation. Upstream fix beats downstream fix: subagents return key facts, citations and confidence, not prose or reasoning chains.
- Three valid escalation triggers: explicit human request, policy gap, no meaningful progress.
- Two unreliable triggers: sentiment and self-rated confidence. Multi-intent and long conversations are not triggers either.
- Explicit "get me a manager" = escalate now. Frustration alone = acknowledge, offer resolution, escalate only if reiterated.
- Angry with no context = acknowledge + one targeted question. Fix already ready = offer resolve or escalate.
- Multi-match identity = ask for email, phone or order ID. Never rank, never pick by recency, never trust a confidence score.
- Structured error = failure type + what was attempted + partial results + alternatives + coverage impact.
- Silent suppression (empty result as success) is the worst pattern — no recovery path. Terminating the whole workflow throws away the partial results.
- Access failure ≠ valid empty result. Retry only the access failure; a valid empty result is the answer. Subagents do local recovery (1–2 retries) before propagating, and never return a generic status.
- Long sessions degrade into "typical patterns": scratchpad file, subagent delegation, phase summaries, manifest, proactive `/compact`. Bigger window and bigger model do not fix attention dilution.
- The manifest is the source of truth across crashes, not the conversation history.
- 97% aggregate accuracy hides stratum failure: validate by document type AND field segment before automating.
- Per-field confidence, calibrated on a labeled validation set, or raw 0.9 means nothing. Sample high-confidence cases post-deployment to catch novel errors.
- Every finding carries claim + URL + document + excerpt + date, through every downstream agent.
- Conflicts are annotated with both values and attribution, then reconciled by the coordinator — never averaged, never picked, never omitted.
- Dates distinguish trends from contradictions. Render by content type: tables for financials, prose for narrative, lists for technical findings.
- A sliding window deletes a turn; a summary rewrites it - either way the number is gone, so the case-facts block is the only copy that survives both.
- Prompt layout is three zones: case-facts at the top, trimmed tool results in the low-attention middle, recap plus policy line plus the live question at the end.
- Explicit human request = escalate now; never resolve-first, never ask why, never offer self-service.
- Only the coordinator may terminate the pipeline; a failing subagent propagates a structured error upward.
- The scratchpad is not created automatically - instruct it in the prompt or CLAUDE.md; the manifest is the checkpoint; /compact cannot run in CI/CD.
- Failures cluster in the low-volume, high-stakes stratum: categorise, sample per stratum, measure per category, route the failing one.
- Provenance is every agent's job - the synthesis step is where it dies.
