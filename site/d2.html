Domain 2 — Tool Design & MCP (18%) — Master Note

Compression layer for tasks 2.1–2.5. Exam: 60 MCQ, 120 min, pass 720/1000, no guessing penalty. Every stem is a production situation followed by "which approach is most effective?". Wrong options are engineered to sound smart, efficient, thorough, helpful, enterprise, simple, or pragmatic. Read the Recall card the morning of the exam.

Task 2.1 — Tool Interface Design

  • Principle: the tool description is the primary mechanism the model uses to select a tool — treat it as selection criteria, not documentation. Write purpose, input format, output format, edge cases, and explicit boundaries vs similar tools. Split any tool whose description contains "or" or "depending on" between behaviours into purpose-specific tools with tight contracts. Split when parameters have interdependent constraints or when action types need different required fields. After fixing descriptions, audit the system prompt for keyword-sensitive instructions that override them.
  • Why the exam wants this: misrouting is a description problem until proven otherwise. It is the cheapest layer that addresses the root cause (edit text before adding infrastructure). A generic multi-purpose tool produces inconsistent output shapes at runtime; a renamed generic tool is still generic — only splitting fixes it. Fix-ranking for misrouting: (1) expand descriptions, (2) few-shot examples, (3) merge tools, (4) train a routing classifier — the last is wrong.
  • Distractors: pre-routing classifier that detects intent before delegation (sounds-smart — adds a component that masks the ambiguity); few-shot examples covering "all possible patterns" (sounds-helpful — treats the symptom, token cost on every call); merge both tools into one universal tool (sounds-simple — loses the semantic distinction and widens the surface); rename the generic tool / add a mode enum (sounds-simple — "description < contract"); expand only one of two colliding descriptions (partial fix).
  • Exact terms: name, description, input_schema (type, properties, required, enum), strict: true (requires additionalProperties: false and all properties in required), input_examples (per daronyondem, when supported). Lookup-then-act: search_projects(query) → archive_project(project_id). Enum for closed sets (knowledge_base, billing_records, support_tickets). Never encode format hints in parameter names (date_string_iso_yyyy_mm_dd) — use descriptions and schemas.
  • Scenario tie-in: Customer Support Resolution Agent — analyze_content vs analyze_document colliding (45% misrouting); get_customer chosen for order questions when descriptions are minimal; a single refund tool serving full refunds, partial refunds, store credits, and exchanges.

Task 2.2 — Structured Error Responses

  • Principle: return structured error metadata with every failure so the agent can decide retry / fix input / escalate. Use isError, errorCategory, isRetryable, a human-readable description, what was attempted, and partial_results. Categories: transient (timeout, 503, rate limit — retryable, retry with the same input), validation (bad format, missing field, malformed ID — retryable only after the agent corrects the input), business (policy limit exceeded, account locked, not eligible — not retryable, surface a customer-friendly description or escalate), permission (401/403, missing scope — not retryable, escalate). A valid empty result is not an error: return isError: false with an empty array and let the agent say "no results".
  • Why the exam wants this: the error contract is the agent's recovery signal. Generic errors ("Operation failed") strip the information the recovery decision needs. Silently returning [] when the backend is down makes the agent report "I found nothing" when the truth is "I couldn't search". Conflating access failure with valid-empty is the canonical 2.2 trap.
  • Distractors: mark everything retryable and let the agent back off (sounds-pragmatic — causes duplicate side effects); increase retry count / max retries / timeout (sounds-efficient — wrong fix for a misclassified empty result); mark a post-submission write timeout as retryable (sounds-pragmatic — duplicate charges and notifications); return a JSON-RPC/protocol error for a business failure (sounds-enterprise); raise an exception so the orchestrator catches it (sounds-simple — frameworks hide exception detail from the model); collapse outcomes into a single coverage percentage (sounds-enterprise — discards which 33% is retryable); abort the whole workflow on one subagent failure (loses partial value).
  • Exact terms: isError: true, errorCategory (transient | validation | business | permission), isRetryable, description (business errors should be customer-friendly — the agent surfaces it), attempted_action / attempted_query, partial_results, next_steps, retry hints retryAfter and maxRetries. MCP error tiers: JSON-RPC protocol errors when the request itself is malformed or the tool cannot be invoked (missing required parameter, unknown method, bad type); tool result with isError: true when the tool ran and the operation failed (remote 404, upstream 503, business rule, permission denial, rate limit). Retry placement: tool-level retry for transient read failures; model-level retry for validation/syntax faults; human approval when a retry may duplicate a side effect.
  • Scenario tie-in: Multi-Agent Research System — web-search subagent times out while others succeed; three source categories returning 15 results, "0 results", and "connection timeout"; Customer Support — get_customer returning [] for both "no such customer" and "database unreachable"; a payment/notification timeout after submission.

Task 2.3 — Tool Distribution and tool_choice

  • Principle: cap each agent at 4–5 role-relevant tools; distribute the rest across specialized subagents. Giving one agent 18 tools degrades selection — the model picks wrong tools or calls unnecessary ones. Scope tools to roles: a synthesis agent gets no web search, a search agent gets no document analysis. When a requirement is "the model must do X first", reach for tool_choice: {"type": "tool", "name": "X"} — a prompt requests, tool_choice requires. For a high-frequency simple capability needed across roles, ship a constrained version with an explicit escalation boundary rather than the full tool.
  • Why the exam wants this: tool count and tool scope are architectural, not stylistic — reliability degrades before the model runs out of context. Constraining capability at the interface makes undesired behaviour impossible rather than discouraged (least privilege). A prompt instruction cannot deliver a deterministic guarantee.
  • Distractors: expand all 18 descriptions (sounds-thorough — the count, not the wording, is the failure); tool_choice: "any" to force commitment (sounds-efficient — the model may pick a different tool); few-shot examples for every tool (sounds-helpful); validate after the fact and re-prompt (sounds-thorough — too late, wrong layer); give the synthesis agent the full web-search toolset (sounds-efficient — over-provisions, blurs roles, adds prompt-injection surface); batch all verification needs to the end (sounds-thorough — unverified claims shape the draft); proactively cache context around every source (sounds-pragmatic — guesses what will be questioned); merge synthesis and coordinator (destroys the architecture); train a smaller model (wrong tool for a tool-design problem). Preferring Grep over a capable MCP tool: do not remove the built-ins first — enhance the MCP description.
  • Exact terms: tool_choice values "auto" (default), "any" (must call some tool), {"type": "tool", "name": "..."} (must call this tool), "none" (text only); disable_parallel_tool_use: true caps one tool call per response. Constrained replacements: fetch_url(url) → load_document(document_url); run_sql(query) → query_orders(filters); send_email(...) → send_customer_notification(template_id, ...). Scoped cross-role tool: verify_fact(claim, max_sources=3) with a description stating that complex multi-source verification routes back to the coordinator. Progressive availability / tool search: {"type": "tool_search_tool_regex_20251119", ...} or the BM25 variant, defer_loading: true on a tool, mcp_toolset default_config, tool_reference blocks. Never defer every tool — at least one must stay non-deferred or the request returns 400 "All tools cannot be deferred"; keep 3–5 hot tools non-deferred; defer_loading: true cannot carry cache_control (400). Per dnacenta's note, forced tool_choice (any and tool) returns 400 on Fable 5.1 / Mythos 5.1 — fall back to auto plus an explicit instruction naming the tool, with strict: true; Opus 5, Sonnet 5, and the 4.x family still accept all four values.
  • Scenario tie-in: Customer Support — a mandatory intent-extraction step skipped on ~15% of turns; an 18-tool agent selecting wrongly; Multi-Agent Research — the synthesis agent returning control for one-line fact checks (85% simple, 15% complex) and adding 2–3 loops at +40% latency.

Task 2.4 — MCP Server Integration

  • Principle: put team-shared servers in project scope (.mcp.json, version-controlled) and personal/experimental servers in user scope (~/.claude.json); never commit secrets — reference them with ${VAR} expansion and document the variable for onboarding. Expose MCP resources as catalogues so the agent reads what data exists instead of burning exploratory tool calls. Prefer a maintained community server for standard integrations; fork or post-process it rather than building from scratch. When an agent ignores a capable MCP tool in favour of a built-in, improve the MCP tool's description — do not delete the built-ins.
  • Why the exam wants this: config scope decides who gets the integration and where credentials live; the fix for a leaked token is parameterisation (and rotating the token), not relocating the file or gitignoring .mcp.json (which defeats team sharing). Resources complement tools: resources are what is true and stable about a system, tools are the actions on it.
  • Distractors: move .mcp.json to ~/.claude.json to fix a credential leak (sounds-simple — the team integration stops being shared); add .mcp.json to .gitignore (sounds-pragmatic — defeats team sharing); have each developer configure the server in user scope (sounds-pragmatic — six setups, no shared source of truth); build a custom proxy/wrapper that reads tokens from .env (sounds-enterprise — "${VAR}" expansion already exists); build a custom MCP server because workflows are specific (sounds-enterprise — evaluate the community server first); a natural-language aggregator tool that re-routes to underlying tools (sounds-smart — hides the real tool surface and worsens selection); preload the whole catalogue into the system prompt (sounds-thorough); remove competing built-in tools (sounds-efficient); trust readOnlyHint as a security control (annotations are untrusted hints — the host must enforce policy in code).
  • Exact terms: .mcp.json at the repo root with mcpServers → { "type", "url", "headers", "timeout", "command", "args", "env" }; ${DATABASE_URL} and ${VAR:-default} expansion; ~/.claude.json (local scope keyed by project path; user scope untied to a project); managed scope managedMcpServers (admin-pushed); scope precedence when names collide is local > project > user, whole entry wins, fields are not merged. Transports: stdio (implied when the entry has command), http / streamable-http (the only remote transport supporting OAuth), sse (legacy), ws (header-only auth). A url with no type is skipped with "has a url but no type" — always set type. Lifecycle: initialize → notifications/initialized → tools/list → tools/call, JSON-RPC 2.0. Server primitives: tools (model-controlled), resources (application-controlled), prompts (user/application-controlled). Client primitives: sampling, elicitation, roots. CLI: claude mcp add --transport http --scope project, --header, --env, claude mcp add-json. Project-scope servers prompt for approval interactively; claude -p and Agent SDK/cloud sessions load them without asking (use disabledMcpjsonServers or --setting-sources). Tool search is on by default for MCP tools; ENABLE_TOOL_SEARCH = unset / true / auto / auto:N / false; alwaysLoad: true exempts a server; tool descriptions and server instructions truncate at 2 KB. Output: warn over 10,000 tokens, truncate at 25,000 by default, raise with MAX_MCP_OUTPUT_TOKENS (warning threshold is fixed). Annotations: readOnlyHint, destructiveHint, idempotentHint, openWorldHint — UI affordances, never a security boundary. list_changed notifications refresh a client's tool list without reconnect. Reserved server names (workspace, claude-in-chrome, computer-use, Claude Preview, Claude Browser) are skipped with a warning. MCP prompts surface as mcp__<server>__<prompt> slash commands.
  • Scenario tie-in: Developer Productivity Tools — six developers, one GitHub MCP server, per-developer tokens, no committed secrets; a code agent probing for available data at session start; an MCP code-analysis tool losing selection to Grep.

Task 2.5 — Built-in Tools

  • Principle: Grep searches file contents (callers, error strings, imports, identifiers) and returns matching lines; Glob matches file paths (extensions, name patterns) and returns paths. Read/Write do whole files; Edit makes targeted changes through a unique text anchor. Build understanding incrementally: Grep for entry points, Read those files, Grep for the identifiers you found, Read only the implementations that matter — never read everything upfront. When tracing a re-exported function, read the wrapper module, list the exports/aliases, then grep each alias; grepping only the original name misses alias callers.
  • Why the exam wants this: the wrong tool makes the task impossible (a path pattern cannot match a function call) or wasteful (reading all files burns tens of thousands of tokens before any reasoning). Edit's failure mode is structural — it needs a unique match — and the escalation ladder, not a different tool category, is the fix.
  • Distractors: Glob first to enumerate all source files, then Grep each (sounds-thorough — inverts seed vs filter when the task is content-seeded); read every file in the directory upfront (sounds-thorough — context-budget killer); spawn one subagent per file, or read in parallel, to go faster (sounds-efficient); index the repo into a vector store (sounds-enterprise); Grep import React to find component files (sounds-smart — that is a path task, use Glob **/*.tsx); use sed/Bash for a targeted edit (wrong tool category); set replace_all: true so every occurrence changes (sounds-simple — changes sites that should not change); delete and recreate the file (destructive); ask the user which files (sounds-helpful).
  • Exact terms: Grep (contents), Glob (**/*.test.ts, src/**/config.*), Read, Write, Edit (old_string/new_string unique-match anchor, replace_all), Bash, WebSearch/WebFetch, Agent, Skill, NotebookEdit, AskUserQuestion, ToolSearch, SendMessage/ListAgents, Workflow. Edit-failure ladder: (1) expand the anchor with surrounding context until unique, (2) if no unique anchor exists, Read the whole file and Write the updated version, (3) if the intent really was every occurrence, replace_all: true. Sequencing rule: Grep first when discovering content, Glob second to narrow paths around the result; mirror form (known file set → check contents) is Glob → Grep. The order depends on which is the seed and which is the filter.
  • Scenario tie-in: Developer Productivity Tools — find all callers of legacyAuth then their test files; trace formatDate through an index.ts re-export under an alias; explore a 120-file codebase without destroying the context window; a targeted config edit whose snippet appears identically six times.

Correlations

Descriptions → selection → schemas → error contracts → recovery. A weak description misroutes the call before any schema or error logic can help, so fix descriptions first. A strong description over an over-broad tool still produces inconsistent output shapes, so split the tool when its contract contains "or". Once the right tool is called, a typed schema (enum, nullable fields, split contracts) keeps the arguments valid. When the tool then fails, the error contract decides what the agent does next: isError: true plus errorCategory and isRetryable drives local recovery, while isError: false with an empty array ends the turn with an honest "no results". Recovery inside a subagent is local and capped — only unresolved failures propagate, carrying what was attempted, partial results, and a recommended action, so the coordinator can retry, reroute, or annotate the gap instead of aborting. Scope sits above all of it: the right tool must also be in the agent's 4–5 tool role set, and the capability must be reachable from the layer being tested (API tool_choice / tools, MCP config, or tool implementation — not a Claude Code hook when the question is API agent design).

Recall card

  • Descriptions are the routing layer, not documentation — expand them first. Misrouting fix order: descriptions → few-shot → merge tools → routing classifier (wrong).
  • "Or" / "depending on" in a description = split the tool. Renaming does not fix it.
  • Misrouting persists after clean descriptions → audit the system prompt for keyword-sensitive instructions.
  • Tool count: 4–5 role-relevant tools per agent. 18 tools degrades selection.
  • "Must do X first" → tool_choice: {"type": "tool", "name": "X"}, never a prompt instruction.
  • "any" guarantees a tool call, not a specific one. "none" = prose with tools still declared.
  • High-frequency simple cross-role need → scoped tool (verify_fact(claim, max_sources=3)) with explicit escalation to the owner.
  • Generic powerful tool → constrained replacement (load_document, query_orders, send_customer_notification).
  • isError: true = the tool couldn't look. isError: false + empty = the tool looked and found nothing. Returning [] when the backend is down is the canonical 2.2 trap.
  • Transient retryable = retry the same input. Validation retryable = retry only after fixing the input. Business and permission errors are never retryable; business errors carry a customer-facing description. A post-submission write timeout is an uncertain outcome, not a retry.
  • Protocol errors (JSON-RPC) = the request never ran. isError: true = the tool ran and the operation failed.
  • Subagent recovers locally (1–2 retries), then propagates only what it cannot resolve, with partial results. The coordinator evaluates partial results; it does not abort on one subagent failure.
  • Project .mcp.json = team, version-controlled. ~/.claude.json = personal (local and user scopes both live there). Collision precedence: local > project > user, whole entry wins.
  • Secrets: ${VAR} expansion in the shared file, plus rotate the leaked token. Never relocate or gitignore the file.
  • Agent probing for available data at conversation start → expose MCP resources as catalogues.
  • Capable MCP tool losing to a built-in → enhance the MCP description; do not remove the built-ins. Standard integration → community server first; fork or post-process, do not build from scratch.
  • MCP annotations (readOnlyHint etc.) are untrusted hints, never a security boundary.
  • Grep = contents. Glob = paths. Content-seeded tasks: Grep then Glob. Path-seeded: Glob then Grep.
  • Edit fails on a non-unique match → expand the anchor first; Read + Write only if no unique anchor exists. Never read every file upfront — Grep entry points, Read selectively, repeat.
  • Wrapper modules: read the wrapper, list exports and aliases, grep each alias — the original name alone misses callers.
